# VPN Manager

Веб-сервис для управления VPN-серверами на клиентских VPS: подключение по SSH, установка
WireGuard/AmneziaWG, управление peers (создание, отзыв, повторное скачивание конфига/QR),
несколько VPS с балансировкой нагрузки и авто-failover, режим моста с собственным доменом,
резервное копирование/восстановление, HTTPS-домен панели, мультитенантность (аккаунты
клиентских организаций).

## Стек
- Backend: NestJS + TypeScript, PostgreSQL (TypeORM), SSH через `node-ssh`
- Frontend: React + Vite + TypeScript + MUI
- Инфраструктура: Docker Compose, Nginx (reverse proxy), certbot (Let's Encrypt)

## Быстрый старт (деплой на сервер)

1. Убедитесь, что на сервере установлены `docker` и `docker compose` (плагин).
2. Скопируйте репозиторий на сервер.
3. Создайте `.env` из примера и заполните секреты:
   ```bash
   cp .env.example .env
   ```
   Обязательно сгенерируйте и впишите:
   - `APP_ENCRYPTION_KEY` — `openssl rand -hex 32`
   - `JWT_SECRET` — любую длинную случайную строку
   - `POSTGRES_PASSWORD`, `SEED_ADMIN_PASSWORD` — надёжные пароли
4. Соберите и запустите:
   ```bash
   docker compose up -d --build
   ```
5. Откройте `http://<адрес-сервера>:<HTTP_PORT>` (по умолчанию порт 80).
6. Войдите под суперадмином — email/пароль из `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD`
   (учётка создаётся автоматически при первом старте, если в базе ещё нет пользователей).

## Как пользоваться

1. **Суперадмин** заходит на вкладку «Серверы» → добавляет VPS (host, SSH-доступ).
   - Если на сервере **уже может быть настроен** WireGuard/AmneziaWG — сначала нажать
     «Проверить существующую установку»: сервис по SSH сам найдёт `wg0.conf`/`awg0.conf`
     по стандартным путям, подключит найденный протокол к учёту (без переустановки и без
     перезапуска интерфейса) и сразу заберёт его peers в базу.
   - Если протокола ещё нет — «Установить протокол» (WireGuard или AmneziaWG, порт, сеть
     вида `10.8.0.0/24`) поставит его с нуля. **Важно**: если на сервере уже был настроен
     VPN, но вы не проверили его через «Проверить существующую установку», «Установить
     протокол» пересоздаст интерфейс с новыми ключами — все существующие peers потеряются.
   - Кнопка «Сканировать/импортировать peers» у уже подключённого протокола донабирает
     peers, которые появились на сервере позже (вручную или другим способом).
   - «Переименовать» — меняет только отображаемое имя в панели, на сам сервер не влияет.
   - «Перезагрузить» — отправляет команду `reboot` по SSH; панель спросит подтверждение
     (все текущие VPN-подключения клиентов к этому серверу оборвутся до его повторной
     загрузки).
   - Цветной чип «на связи» / «нет связи» / «проверяем связь…» у каждого сервера — живой
     статус, обновляется через тот же периодический SSH-опрос, что и Дашборд, без ручного
     обновления страницы.
   - Если сервер отмечен предупреждением **«нужны новые SSH-данные»** — сохранённый
     пароль/ключ не расшифровывается текущим ключом шифрования панели (обычно после
     восстановления БД на другом сервере, см. «Резервное копирование и восстановление»
     ниже). Нажмите «Ввести заново» на карточке сервера и укажите актуальные учётные
     данные — после сохранения панель снова сможет управлять сервером по SSH.
   - Удаление сервера — полная зачистка: все его peers деактивируются и удаляются,
     установленные на нём протоколы удаляются из панели. Если сервер служил upstream для
     какого-то моста, мост автоматически переключается на другой доступный сервер того же
     протокола (см. «Режим моста»). SSH на сам удаляемый сервер при этом не дёргается —
     сервер обычно удаляют именно потому, что он недоступен/выводится из эксплуатации.
2. Суперадмин создаёт **организацию** (клиентскую компанию) — вкладка «Организации»,
   при создании сразу заводится администратор этой организации (email/пароль).
3. Клиент логинится под своим `org_admin`-аккаунтом, заходит на вкладку **Peers**, создаёт
   нужное число VPN-учёток (сервер выбирается автоматически балансировщиком нагрузки —
   по наименее загруженному серверу с установленным протоколом), скачивает конфиг/QR.
4. Организация может заводить себе дополнительных пользователей (`org_user`) на вкладке
   «Пользователи» — они видят и создают только peers своей организации.

## Режим моста

Панель может поднять WireGuard/AmneziaWG **на своей же машине** (self-сервер, хост, где
крутится сама панель) — клиенты подключаются к этому мосту обычным клиентом, а мост
маршрутизирует их трафик через один из уже добавленных backend-серверов (общий
upstream-туннель на всех клиентов моста).

Базовая настройка:

1. На хосте, где развёрнута панель, должен быть поднят `sshd` (это ручной шаг — панель
   сама себя по SSH не настраивает). Добавьте его на вкладке «Серверы» как обычный сервер,
   указав его собственный адрес.
2. На вкладке «Мост» создайте мост, выбрав этот сервер как self-сервер, порт и сеть для
   клиентов моста (например `10.9.0.0/24`) — можно сразу для WireGuard и AmneziaWG
   одновременно, тогда мост будет выдавать клиентам оба протокола через один и тот же
   upstream. На одном self-сервере можно создать несколько мостов (разные порты) — например,
   отдельный мост на каждую организацию.
3. Выберите upstream — уже добавленный backend-сервер/протокол, через который мост будет
   выпускать трафик своих клиентов (выпадающий список «Переключить upstream вручную»).
   Панель заведёт на нём системный peer (общий на всех клиентов моста), поднимет на
   self-сервере интерфейс в роли клиента к этому серверу и настроит NAT/forwarding между
   ним и клиентским интерфейсом.
4. Peers для клиентов моста создаются как обычные peers (вкладка Peers, сервер = мост) — по
   тем же правилам организаций, что и любые другие.

### Режимы переключения upstream

У моста три режима (переключатель «Режим upstream» на карточке моста):

- **Ручной** — upstream меняется только явно, кнопкой «Переключить».
- **Авто (по нагрузке)** — раз в 5 минут панель сравнивает загрузку текущего upstream с
  другими ACTIVE серверами того же протокола и переключается, если находит заметно менее
  загруженный. Доступен только после первого ручного назначения upstream.
- **Failover (по доступности)** — переключается не по нагрузке, а по факту доступности
  сервера. Настраивается отдельно от простого выбора upstream:
  1. В разделе «Приоритет upstream» на карточке моста нажмите «Настроить» и отметьте один
     сервер как «Основной», а любое число других — как «Резерв 1», «Резерв 2» и т.д. по
     убыванию предпочтения, затем «Сохранить».
  2. Переключите «Режим upstream» на «Failover» (доступно только когда в списке приоритета
     есть хотя бы один сервер).
  3. Дальше панель каждые ~20 секунд проверяет доступность каждого кандидата (лёгкое
     TCP-подключение к его SSH-порту — быстрая проверка «жив ли сервер вообще», без полной
     SSH-сессии; сам VPN-порт для такой проверки не годится — WireGuard/AmneziaWG работают
     по UDP и намеренно не отвечают на произвольные пакеты) и держит upstream на первом
     доступном по приоритету. Если основной сервер снова станет доступен — мост
     автоматически вернётся на него. Чтобы не дёргаться на случайной сетевой заминке,
     сервер считается упавшим/восстановившимся только после 3 проверок подряд с одним и тем
     же результатом (то есть реакция занимает около минуты, не мгновенно).
  4. Живой статус доступности каждого кандидата виден прямо в списке приоритета (чип
     «доступен» / «недоступен» / «проверяем…»).

Переключение upstream (в любом режиме) НЕ разрывает уже подключённых клиентов моста — их
собственный интерфейс не трогается, меняется только маршрут за ним.

### Доменное имя моста

У моста можно задать собственное доменное имя (кнопка «Изменить» на карточке моста, поле
«Доменное имя моста») — если оно задано, все скачиваемые клиентские конфиги peers этого
моста используют домен вместо IP self-сервера в строке `Endpoint`. Это отдельная настройка
от домена самой панели (см. ниже «Домен и HTTPS панели») — здесь речь про VPN-эндпоинт,
к которому подключаются клиенты, а не про веб-адрес админки.

Смысл: если self-сервер когда-нибудь придётся перенести на другой хост/IP (авария,
переезд), достаточно перевести DNS-запись домена на новый IP — уже выданные клиентам
конфиги продолжат работать без переустановки, потому что в них записан домен, а не
конкретный адрес. См. также «Резервное копирование и восстановление» — оба механизма
рассчитаны на совместное использование в сценарии полного восстановления после потери
сервера.

### Важно: self-сервер внутри LXC-контейнера

Если панель сама развёрнута в **непривилегированном** Proxmox LXC-контейнере (как в этом
деплое), поднять на нём реальный WireGuard-интерфейс, скорее всего, не получится — ядро
делит netlink/capability-проверки для WireGuard так, что `wg-quick` там нестабильно падает
с segfault (не баг панели — воспроизводится и при ручном запуске в шелле). Рабочих вариантов
два: (а) вынести self-сервер на отдельную VM/железный хост, (б) сделать LXC-контейнер
**привилегированным** — но это заметно снижает изоляцию контейнера от хоста и требует также
`lxc.apparmor.profile: unconfined` и `lxc.cap.drop:` (пустое значение) в конфиге контейнера
на Proxmox, иначе Docker внутри не сможет стартовать (AppArmor-профиль `docker-default` не
загрузится без этих настроек). Это осознанный компромисс безопасности — принимайте его сами.

### Важное ограничение первого билда
Полностью скачать конфиг (с приватным ключом) можно только для peers, **созданных через
сервис** — приватный ключ шифруется и хранится в БД. Peers, которые сервис нашёл на сервере
при сканировании (`source: imported`), в конфиге на сервере физически не содержат приватный
ключ клиента (так устроен WireGuard) — такие записи можно только отозвать и создать взамен
новый peer через сервис.

## Домен и HTTPS панели

Вкладка «Настройки» → раздел «Домен и HTTPS» позволяет открыть саму панель по HTTPS с
автоматически выпускаемым и обновляемым сертификатом Let's Encrypt — не путать с доменным
именем моста выше (это про веб-адрес самой админки, а не про VPN-эндпоинт клиентов).

Как включить:

1. Заранее направьте A-запись домена на IP сервера, где развёрнута панель.
2. В разделе «Домен и HTTPS» укажите домен и email (нужен Let's Encrypt для уведомлений об
   истечении, если автообновление вдруг перестанет работать) и нажмите «Сохранить».
3. Включите переключатель «HTTPS» — панель сама запросит сертификат и, если выпуск прошёл
   успешно, начнёт обслуживать HTTPS на 443 порту. Если выпуск не удался (например, домен
   ещё не успел разрешиться в DNS) — ошибка покажется под переключателями, а панель
   останется доступна по HTTP как ни в чём не бывало.
4. Порт 80 остаётся открытым даже при включённом HTTPS — по нему идёт редирект на HTTPS и
   проверка домена при автообновлении сертификата (без него сертификат Let's Encrypt
   переставал бы обновляться сам собой примерно раз в 2-3 месяца).
5. Переключатель «HTTP» можно выключить отдельно (тогда порт 80 отдаёт только редирект,
   ничего больше) — но нельзя выключить одновременно и HTTP, и HTTPS, панель это не
   позволит, чтобы не заблокировать саму себя.
6. Кнопка «Обновить сертификат сейчас» форсирует внеплановое обновление (обычно не нужна —
   сертификат обновляется сам за несколько недель до истечения), срок действия текущего
   сертификата виден там же.

Технические детали и почему это устроено именно так — в `CLAUDE.md`.

## Резервное копирование и восстановление

Вкладка «Настройки» → раздел «Резервная копия базы данных».

- **Скачать бэкап** — кнопка выгружает дамп PostgreSQL (`.sql`) напрямую в браузер, без
  промежуточного хранения на сервере. В дампе — все данные (организации, пользователи,
  серверы, мосты, peers), **кроме** самого приложения/кода и кроме ключа шифрования
  `APP_ENCRYPTION_KEY` (он в дамп не входит — см. ниже).
- **Восстановление** — загружает выбранный `.sql`-файл и **полностью заменяет им текущую
  базу данных**. Это необратимо: все текущие данные, которых нет в файле, будут потеряны.
  Панель попросит ввести подтверждающее слово перед запуском. После восстановления backend
  сам перезапускается (несколько секунд недоступности — это ожидаемо).

Сценарий использования — переезд на новый сервер после аварии/потери старого:

1. Разверните панель на новом сервере обычным способом («Быстрый старт» выше).
2. В настройках нового деплоя загрузите файл, скачанный со старого сервера через
   «Резервное копирование».
3. Если у мостов настроено доменное имя (см. «Доменное имя моста» выше) — переведите DNS
   этого домена на IP нового сервера. Старые клиентские конфиги peers продолжат работать
   без переустановки.
4. SSH-пароли/ключи добавленных серверов зашифрованы ключом `APP_ENCRYPTION_KEY` **того
   деплоя, где они создавались** — если на новом сервере в `.env` стоит другой ключ, эти
   пароли не расшифруются. Панель сама это заметит: такие серверы будут отмечены
   предупреждением «нужны новые SSH-данные» (вкладка «Серверы»), там же — форма, чтобы
   ввести пароль/ключ заново. Программного переноса самого ключа шифрования между
   деплоями нет — это осознанное решение (файл бэкапа и ключ шифрования специально
   остаются раздельными секретами, чтобы утечка одного файла не раскрывала оба сразу).
   Если хотите, чтобы всё расшифровалось сразу без переввода — скопируйте значение
   `APP_ENCRYPTION_KEY` из `.env` старого сервера в `.env` нового ДО восстановления.
5. Приватные ключи уже существующих peers (не серверов) при смене ключа шифрования
   восстановить нельзя в принципе — такие peers придётся отозвать и выдать заново. Сами
   уже подключённые VPN-клиенты при этом не отключаются — их локальный конфиг с ключами
   никуда не делся, теряется только возможность скачать/пересоздать его из панели.

### Известные ограничения MVP / что дальше
- Поддерживаются только сети вида `a.b.c.0/24` (до 253 клиентов на интерфейс/протокол).
- TypeORM работает в режиме `synchronize: true` (без ручных миграций) — удобно для первого
  разворачивания, но перед серьёзной продакшен-эксплуатацией стоит перейти на миграции.
- Установка AmneziaWG зависит от доступности PPA `ppa:amnezia/ppa` и совместимости ядра
  VPS-провайдера — на части хостингов (кастомные ядра без dkms) установка может не пройти;
  в этом случае протокол на сервере помечается статусом `error` с текстом ошибки в интерфейсе.
- «Проверить существующую установку» ищет конфиг: сначала по стандартным путям на хосте
  (`/etc/wireguard/*.conf`, `/etc/amnezia/amneziawg/*.conf`), затем — среди Docker-контейнеров
  официального self-hosted сервера AmneziaVPN (имя контейнера содержит `amnezia-wireguard`
  или `amnezia-awg`; конфиг ищется внутри контейнера в `/opt/amnezia/**/*.conf`). Берётся
  первый найденный файл/контейнер — нестандартные установки (другой путь, несколько
  интерфейсов одного протокола на сервере) не обнаруживаются автоматически. Для
  контейнерных установок команды на сервере выполняются через `docker exec`.
- AmneziaWG 2.0 добавляет параметры `S3`/`S4`, а `H1`-`H4` там могут быть диапазоном
  `min-max` вместо одного числа — при обнаружении такие значения сохраняются как есть
  (не только как целые числа), при выдаче клиентского конфига возвращаются в исходном виде.
- Создание/отзыв peers через панель для протоколов, обнаруженных внутри стороннего Docker-
  контейнера (`execContainer`, например self-hosted сервер AmneziaVPN), **работает** — но
  первая версия этой логики на реальном продакшен-контейнере испортила файл конфига на диске
  (интерфейс хоста в `PostUp`/`PostDown` не существовал в netns контейнера) и оставила в БД
  peer, которого на сервере не было; сам туннель при этом не оборвался. Починено: для
  `execContainer`-протоколов `PostUp`/`PostDown` не добавляются вовсе, egress-интерфейс для
  MASQUERADE определяется внутри контейнера, исходный `Address` из найденного конфига
  сохраняется как есть, при сбое применения peer откатывается из БД. Перепроверено на живом
  сервере (создание + отзыв, два реальных подключённых клиента не пострадали).
- `wg-quick`/`awg-quick` внутри driver'ов вызываются напрямую (`{quickBinary} up <путь-к-conf>`),
  а не через `systemctl ... --now` — на части хостов (замечено на self-хосте для режима
  моста, вложенный Proxmox LXC) запуск именно через systemd приводил к segfault в самом
  wg-quick при операциях с WireGuard-интерфейсом. Юнит всё равно создаётся и включается
  (`systemctl enable`, без `--now`) для автозапуска при обычной перезагрузке хоста.
- AmneziaWG зависит от PPA `ppa:amnezia/ppa`, который может не иметь сборки под конкретную
  версию Ubuntu (например, ещё не собран под 26.04 «resolute» на момент этого билда) —
  установка в этом случае завершится ошибкой с текстом от `apt-get` в интерфейсе.
- Проверка доступности кандидатов для Failover-режима моста (см. выше) — это TCP-пинг
  SSH-порта сервера, а не самого VPN-порта (технически невозможно для WireGuard/AmneziaWG,
  см. выше). Если на сервере когда-нибудь заблокируют SSH-порт, но VPN-порт при этом
  останется открытым (или наоборот), Failover-режим будет ошибаться в оценке доступности —
  такой сценарий считается редким и осознанно не обрабатывается отдельно.

## Настройки сервера (вкладка «Настройки»)

- **Домен и HTTPS** — см. раздел «Домен и HTTPS панели» выше.
- **Резервная копия базы данных** — см. раздел «Резервное копирование и восстановление» выше.
- **Логи** — просмотр и скачивание логов любого из 4 контейнеров стека (`backend`,
  `frontend`, `nginx`, `postgres`) прямо из интерфейса: выбрать сервис и число последних
  строк, «Показать» — выводит в панели, «Скачать (.log)» — сохраняет файлом. Полезно, когда
  нет под рукой SSH-доступа к серверу.
- **Самообновление по кнопке** — тянет `git pull` и пересобирает стек прямо из
  веб-интерфейса, с индикатором прогресса в процентах. Для этого backend-контейнер получает
  доступ к `/var/run/docker.sock` хоста и к самому репозиторию по тому же пути, что и на
  хосте (`docker-compose.yml`, переменная `REPO_PATH: ${PWD}`) — **это осознанный компромисс
  безопасности**: доступ к docker-сокету изнутри контейнера равносилен root на хосте.
  Обязательно запускать `docker compose up -d --build` из корня репозитория (как и описано
  в «Быстром старте» выше) — иначе `${PWD}` укажет не туда и обновление не сможет корректно
  пересобрать стек. Если такой уровень доступа неприемлем для вашей модели угроз — уберите
  две строки `volumes` (`docker.sock` и `${PWD}:${PWD}`) и `REPO_PATH` у сервиса `backend` в
  `docker-compose.yml`; всё остальное в панели (включая бэкап БД) продолжит работать,
  перестанет работать только кнопка «Обновить». Вывод обновления пишется в `update.log` в
  корне репозитория на хосте — можно посмотреть по SSH, если что-то пошло не так.
  Если после нажатия «Обновить» сайт вдруг перестал открываться — зайдите по SSH в каталог
  репозитория и выполните `docker compose up -d`: команда безопасна для повторного запуска,
  сама доведёт до консистентного состояния всё, что обновление не успело закончить.

Если backend панели по какой-то причине недоступен (например, самообновление ещё не
закончилось) — сверху любой страницы (включая страницу входа) появляется предупреждающий
баннер «Backend недоступен»; он исчезает сам, как только backend снова ответит — обновлять
страницу вручную не нужно.

## Локальная разработка
```bash
# backend
cd backend && npm install && npm run start:dev

# frontend
cd frontend && npm install && npm run dev
```
Backend слушает `:3000`, frontend dev-сервер — `:5173` (нужно поднять свой Postgres и
прописать `DB_*`/`JWT_SECRET`/`APP_ENCRYPTION_KEY` в окружении backend вручную для локального запуска).
