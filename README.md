# VPN Manager

Веб-сервис для управления VPN-серверами на клиентских VPS: подключение по SSH, установка
WireGuard/AmneziaWG, управление peers (создание, отзыв, повторное скачивание конфига/QR),
несколько VPS с балансировкой нагрузки, мультитенантность (аккаунты клиентских организаций).

## Стек
- Backend: NestJS + TypeScript, PostgreSQL (TypeORM), SSH через `node-ssh`
- Frontend: React + Vite + TypeScript + MUI
- Инфраструктура: Docker Compose, Nginx (reverse proxy)

## Быстрый старт (деплой на сервер)

1. Убедитесь, что на сервере установлены `docker` и `docker compose` (плагин).
2. Скопируйте репозиторий на сервер.
3. Создайте `.env` из примера и заполните секреты:
   ```bash
   cp .env.example .env
   ```
   Обязательно сгенерируйте и впишите:
   - `APP_ENCRYPTION_KEY` — `openssl rand -hex 32`
   - `JWT_SECRET` — любую длинную случайную строку
   - `POSTGRES_PASSWORD`, `SEED_ADMIN_PASSWORD` — надёжные пароли
4. Соберите и запустите:
   ```bash
   docker compose up -d --build
   ```
5. Откройте `http://<адрес-сервера>:<HTTP_PORT>` (по умолчанию порт 80).
6. Войдите под суперадмином — email/пароль из `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD`
   (учётка создаётся автоматически при первом старте, если в базе ещё нет пользователей).

## Как пользоваться

1. **Суперадмин** заходит на вкладку «Серверы» → добавляет VPS (host, SSH-доступ).
   - Если на сервере **уже может быть настроен** WireGuard/AmneziaWG — сначала нажать
     «Проверить существующую установку»: сервис по SSH сам найдёт `wg0.conf`/`awg0.conf`
     по стандартным путям, подключит найденный протокол к учёту (без переустановки и без
     перезапуска интерфейса) и сразу заберёт его peers в базу.
   - Если протокола ещё нет — «Установить протокол» (WireGuard или AmneziaWG, порт, сеть
     вида `10.8.0.0/24`) поставит его с нуля. **Важно**: если на сервере уже был настроен
     VPN, но вы не проверили его через «Проверить существующую установку», «Установить
     протокол» пересоздаст интерфейс с новыми ключами — все существующие peers потеряются.
   - Кнопка «Сканировать/импортировать peers» у уже подключённого протокола донабирает
     peers, которые появились на сервере позже (вручную или другим способом).
2. Суперадмин создаёт **организацию** (клиентскую компанию) — вкладка «Организации»,
   при создании сразу заводится администратор этой организации (email/пароль).
3. Клиент логинится под своим `org_admin`-аккаунтом, заходит на вкладку **Peers**, создаёт
   нужное число VPN-учёток (сервер выбирается автоматически балансировщиком нагрузки —
   по наименее загруженному серверу с установленным протоколом), скачивает конфиг/QR.
4. Организация может заводить себе дополнительных пользователей (`org_user`) на вкладке
   «Пользователи» — они видят и создают только peers своей организации.

## Режим моста

Панель может поднять WireGuard **на своей же машине** (хост, где крутится сама панель) —
клиенты подключаются к этому мосту обычным WireGuard-клиентом, а мост маршрутизирует их
трафик через один из уже добавленных backend-серверов (общий upstream-туннель на всех
клиентов моста, без обфусцированного клиента на стороне конечного устройства).

Как настроить:

1. На хосте, где развёрнута панель, должен быть поднят `sshd` (это ручной шаг — панель
   сама себя по SSH не настраивает). Добавьте его на вкладке «Серверы» как обычный сервер,
   указав его собственный адрес.
2. На вкладке «Мост» создайте мост, выбрав этот сервер как self-сервер, порт и сеть для
   клиентов моста (например `10.9.0.0/24`) — панель поставит на нём обычный WireGuard тем
   же способом, что и на любом другом сервере.
3. Выберите upstream — уже добавленный backend-сервер/протокол, через который мост будет
   выпускать трафик своих клиентов. Панель заведёт на нём системный peer (общий на всех
   клиентов моста), поднимет на self-сервере интерфейс `wg-upstream0` в роли клиента к
   этому серверу и настроит NAT/forwarding между `wg-upstream0` и клиентским интерфейсом.
4. Режим можно переключить на «Авто» (доступно только после первого ручного назначения
   upstream) — раз в 5 минут панель сравнивает загрузку текущего upstream с другими ACTIVE
   серверами того же протокола и переключается, если находит заметно менее загруженный
   (переключение upstream НЕ разрывает уже подключённых клиентов моста — их собственный
   интерфейс не трогается, меняется только маршрут за ним).
5. Peers для клиентов моста создаются как обычные peers (вкладка Peers, сервер = мост) — по
   тем же правилам организаций, что и любые другие.

### Важно: self-сервер внутри LXC-контейнера

Если панель сама развёрнута в **непривилегированном** Proxmox LXC-контейнере (как в этом
деплое), поднять на нём реальный WireGuard-интерфейс, скорее всего, не получится — ядро
делит netlink/capability-проверки для WireGuard так, что `wg-quick` там нестабильно падает
с segfault (не баг панели — воспроизводится и при ручном запуске в шелле). Рабочих вариантов
два: (а) вынести self-сервер на отдельную VM/железный хост, (б) сделать LXC-контейнер
**привилегированным** — но это заметно снижает изоляцию контейнера от хоста и требует также
`lxc.apparmor.profile: unconfined` и `lxc.cap.drop:` (пустое значение) в конфиге контейнера
на Proxmox, иначе Docker внутри не сможет стартовать (AppArmor-профиль `docker-default` не
загрузится без этих настроек). Это осознанный компромисс безопасности — принимайте его сами.

### Важное ограничение первого билда
Полностью скачать конфиг (с приватным ключом) можно только для peers, **созданных через
сервис** — приватный ключ шифруется и хранится в БД. Peers, которые сервис нашёл на сервере
при сканировании (`source: imported`), в конфиге на сервере физически не содержат приватный
ключ клиента (так устроен WireGuard) — такие записи можно только отозвать и создать взамен
новый peer через сервис.

### Известные ограничения MVP / что дальше
- Поддерживаются только сети вида `a.b.c.0/24` (до 253 клиентов на интерфейс/протокол).
- TypeORM работает в режиме `synchronize: true` (без ручных миграций) — удобно для первого
  разворачивания, но перед серьёзной продакшен-эксплуатацией стоит перейти на миграции.
- TLS/HTTPS настраивается из вкладки «Настройки» → «Домен и HTTPS»: указать домен
  (направленный A-записью на сервер) и email, включить HTTPS — сертификат Let's Encrypt
  выпускается и обновляется автоматически. По умолчанию (без домена) панель работает по
  чистому HTTP.
- Установка AmneziaWG зависит от доступности PPA `ppa:amnezia/ppa` и совместимости ядра
  VPS-провайдера — на части хостингов (кастомные ядра без dkms) установка может не пройти;
  в этом случае протокол на сервере помечается статусом `error` с текстом ошибки в интерфейсе.
- «Проверить существующую установку» ищет конфиг: сначала по стандартным путям на хосте
  (`/etc/wireguard/*.conf`, `/etc/amnezia/amneziawg/*.conf`), затем — среди Docker-контейнеров
  официального self-hosted сервера AmneziaVPN (имя контейнера содержит `amnezia-wireguard`
  или `amnezia-awg`; конфиг ищется внутри контейнера в `/opt/amnezia/**/*.conf`). Берётся
  первый найденный файл/контейнер — нестандартные установки (другой путь, несколько
  интерфейсов одного протокола на сервере) не обнаруживаются автоматически. Для
  контейнерных установок команды на сервере выполняются через `docker exec`.
- AmneziaWG 2.0 добавляет параметры `S3`/`S4`, а `H1`-`H4` там могут быть диапазоном
  `min-max` вместо одного числа — при обнаружении такие значения сохраняются как есть
  (не только как целые числа), при выдаче клиентского конфига возвращаются в исходном виде.
- Создание/отзыв peers через панель для протоколов, обнаруженных внутри стороннего Docker-
  контейнера (`execContainer`, например self-hosted сервер AmneziaVPN), **работает** — но
  первая версия этой логики на реальном продакшен-контейнере испортила файл конфига на диске
  (интерфейс хоста в `PostUp`/`PostDown` не существовал в netns контейнера) и оставила в БД
  peer, которого на сервере не было; сам туннель при этом не оборвался. Починено: для
  `execContainer`-протоколов `PostUp`/`PostDown` не добавляются вовсе, egress-интерфейс для
  MASQUERADE определяется внутри контейнера, исходный `Address` из найденного конфига
  сохраняется как есть, при сбое применения peer откатывается из БД. Перепроверено на живом
  сервере (создание + отзыв, два реальных подключённых клиента не пострадали).
- `wg-quick`/`awg-quick` внутри driver'ов вызываются напрямую (`{quickBinary} up <путь-к-conf>`),
  а не через `systemctl ... --now` — на части хостов (замечено на self-хосте для режима
  моста, вложенный Proxmox LXC) запуск именно через systemd приводил к segfault в самом
  wg-quick при операциях с WireGuard-интерфейсом. Юнит всё равно создаётся и включается
  (`systemctl enable`, без `--now`) для автозапуска при обычной перезагрузке хоста.
- AmneziaWG зависит от PPA `ppa:amnezia/ppa`, который может не иметь сборки под конкретную
  версию Ubuntu (например, ещё не собран под 26.04 «resolute» на момент этого билда) —
  установка в этом случае завершится ошибкой с текстом от `apt-get` в интерфейсе.

## Настройки сервера (вкладка «Настройки»)

- **Бэкап БД** — кнопка скачивает дамп `pg_dump` (`.sql`) напрямую, без промежуточного
  хранения на сервере.
- **Самообновление по кнопке** — тянет `git pull` и пересобирает стек
  (`docker compose up -d --build`) прямо из веб-интерфейса. Для этого backend-контейнер
  получает доступ к `/var/run/docker.sock` хоста и к самому репозиторию по тому же пути,
  что и на хосте (`docker-compose.yml`, переменная `REPO_PATH: ${PWD}`) — **это осознанный
  компромисс безопасности**: доступ к docker-сокету изнутри контейнера равносилен root на
  хосте. Обязательно запускать `docker compose up -d --build` из корня репозитория (как и
  описано в «Быстром старте» выше) — иначе `${PWD}` укажет не туда и обновление не сможет
  корректно пересобрать стек. Если такой уровень доступа неприемлем для вашей модели угроз —
  уберите две строки `volumes` (`docker.sock` и `${PWD}:${PWD}`) и `REPO_PATH` у сервиса
  `backend` в `docker-compose.yml`; всё остальное в панели (включая бэкап БД) продолжит
  работать, перестанет работать только кнопка «Обновить». Вывод обновления пишется в
  `update.log` в корне репозитория на хосте — можно посмотреть по SSH, если что-то пошло не так.

## Локальная разработка
```bash
# backend
cd backend && npm install && npm run start:dev

# frontend
cd frontend && npm install && npm run dev
```
Backend слушает `:3000`, frontend dev-сервер — `:5173` (нужно поднять свой Postgres и
прописать `DB_*`/`JWT_SECRET`/`APP_ENCRYPTION_KEY` в окружении backend вручную для локального запуска).
